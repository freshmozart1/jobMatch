# jobMatch prototype review — 2026-09-02

Reviewed as a first-time user of jobMatch (Vue 3 frontend) against a locally running jobMatchServer (Node/Express + MongoDB + OpenAI + Python token service), all started fresh for this review. Full review scope: search/scrape, swipe deck, match filter, Application Editor, cover letter generation, CV upload, downloads, edge cases. Live LinkedIn scraping was used (with your approval) instead of seeded data.

All three scrapes in this review used a single keyword (`software engineer`, Berlin, 25 km). Multi-keyword search (comma-separated, e.g. `react, typescript`) was not tested — findings #2–#4 below are confirmed only for the single-keyword path; whether the failure rate, hang, or reload behavior differs when multiple keywords are scraped per request is unknown.

Screenshots referenced below were viewed live during the session; they cannot be attached to GitHub issues, so visual evidence is described in words.

## Findings

### 1. Like/Dislike buttons on the swipe deck do nothing (Blocker)

**Journey:** Core swipe/rate flow — the reason the app exists.
**Repro:**
1. Search for `software engineer` in Berlin, wait for jobs to load on `/`.
2. With a job card on top, click the pink thumbs-down ("Dislike") button below the deck, or the green thumbs-up ("Like") button.

**Expected:** The card animates away, the deck advances to the next card, and the like/dislike is persisted (`POST /jobs/create`).
**Actual:** Nothing happens. The same card stays on top. Verified three times (two separate button clicks, one isolated element-ref click) via the accessibility tree (identical DOM/links before and after) and via the network log (zero requests fired). Immediately afterwards, dragging the same card to the right correctly advanced the deck **and** fired `POST /jobs/create` → `201`. So the drag/swipe gesture works; only the two buttons are dead.
**Why a user cares:** On desktop (no touch), or for anyone who doesn't realize the card itself is draggable, the app is completely unusable — there is no visible way to move past the first card. The buttons are the only affordance suggested by their icons; a first-time user has no reason to try dragging a "button row" instead of clicking it.
**Suspected cause (guess):** The click handlers on `JobCardStack.vue`'s like/dislike buttons look wired to a different state than the drag gesture's handler, or aren't wired at all — worth checking whether the buttons dispatch the same action the drag-end handler does.

### 2. Live LinkedIn scrapes silently discard most results, with zero feedback to the user (Blocker/Major)

**Journey:** First-time search.
**Repro:** Search `software engineer` / Berlin / 25 km / past 24h, submit, watch the backend log.
**Expected:** Scraped jobs stream into the deck; if something can't be used, the user learns why or at least that something went wrong.
**Actual:** Across two separate live scrapes (~30 job indices attempted each), the backend logged lines like:
```
LinkedIn scrape result for job index 4 is suspect (companyMismatch=true, sourceJobIdMismatch=true, lateOverlayDetected=false); not forwarding it.
```
for roughly 10 of ~30 job indices per run — over a third of results silently dropped. None of this reaches the frontend: no partial-failure banner, no "some results were skipped" note, nothing in the Network tab either (these jobs are never sent over the SSE stream at all). The user just ends up with a very sparse deck (2–4 cards from a ~30-job scrape) and no way to know that most of the search's results were thrown away, or why.
**Why a user cares:** The app looks like it barely found anything, when in fact it found plenty and quietly rejected it. A user has no way to distinguish "there just aren't many matching jobs" from "the scraper is malfunctioning."
**Suspected cause (guess):** Either LinkedIn is serving an interstitial/decoy for a meaningful fraction of job cards during unauthenticated scraping, or the detail-pane read is racing the list click. Either way, the safety check in `scrapeJob.ts` that discards "suspect" results has no matching signal on the frontend.

### 3. A scrape can hang indefinitely with the UI stuck on "Loading jobs…" (Major)

**Journey:** First-time search (same as above).
**Repro:** Same search as #2.

**Directly observed** (Playwright's action trace, printed by the `linkedin-job-scraper` package while clicking into a job card):
```
- waiting for locator('ul.jobs-search__results-list > li').filter({ has: locator('h3') }).nth(1)
- locator resolved to <li>...</li>
- attempting click action
- element is visible, enabled and stable
- scrolling into view if needed
- done scrolling
- <div aria-hidden="false" class="modal__overlay flex items-center bg-color-background-scrim
    justify-center fixed bottom-0 left-0 right-0 top-0 opacity-0 invisible pointer-events-none
    z-[1000] ... modal__overlay--visible">...</div> from <div class="top-level-modal-container">...</div>
    subtree intercepts pointer events
- retrying click action
- waiting 100ms / 500ms / 20ms ...
```
A click on a `<li>` job-list item is repeatedly blocked because a `<div class="modal__overlay ... top-level-modal-container">` sits over it and (per the browser) intercepts the pointer event — despite that div's own class list including `opacity-0 invisible pointer-events-none`, which suggests a `modal__overlay--visible` modifier class is overriding those base styles at runtime and making it interactive. This retry loop ran for 7+ minutes with **no forward progress at all** on one job (two terminal screenshots taken 2 minutes apart were byte-identical); on a different job in the same run it eventually gave up after a hard 4000ms timeout ("`locator.click: Timeout 4000ms exceeded`"). The frontend sat on the "Loading jobs…" empty state the entire time; `get_page_text` confirmed no content ever rendered.

**Inferred, not confirmed:** that this overlay is a LinkedIn sign-in/interstitial ("join LinkedIn") prompt. I did not verify this directly — the scrape runs in its own separate, automated browser instance ("Google Chrome for Testing") that I deliberately left untouched (to avoid disturbing the in-progress scrape or accidentally triggering a login attempt/CAPTCHA), so I never saw the overlay's actual on-screen content. The inference rests on: (a) the scrape is unauthenticated — the README lists "Authenticated LinkedIn session support" as not yet implemented, and LinkedIn is known to show sign-in walls to anonymous visitors; (b) jobMatchServer already has its own detection for this — job index 0 in the same run was flagged `lateOverlayDetected=true`, implying the developers are aware overlays can appear mid-scrape; (c) the generic `modal__overlay` / `top-level-modal-container` class names look like LinkedIn's own modal-portal markup rather than anything jobMatchServer renders itself. Worth confirming directly (e.g. a screenshot of the scraper's browser next time this happens) before assuming the exact cause.

**Expected:** Either a bounded timeout that drops the stuck job and moves on, or visible progress/an error surfaced to the user well before minute 7.
**Actual:** No timeout observed within 7 minutes on the stuck job; no UI feedback of any kind. The only way out was to close the tab (which the backend did correctly detect — logged "LinkedIn scrape aborted: client disconnected" — so the abort-on-disconnect fix from issue #117 is working). A user without dev tools open would have no idea the app hasn't just frozen.
**Why a user cares:** A multi-minute silent hang with no cancel button and no indication of what's happening reads as "the app is broken," and a user will likely just close the tab and give up rather than wait it out.

### 4. Every page load restarts the live scrape from scratch (Major, compounds #2/#3)

**Repro:** With a search already saved (keywords persist in `localStorage` per the README), reload `/` or open a fresh tab to it.
**Actual:** The app always shows "Loading jobs…" and kicks off a brand-new `POST /scrape/linkedin` — previously-fetched job cards from earlier in the session are not shown, even briefly, while the new scrape runs.
**Why a user cares:** Combined with #2 and #3, a reload (e.g. after a genuine crash, or just because a user is checking back later) is expensive and risks reproducing the multi-minute hang again, discarding a deck the user may already have been part-way through.

### 5. No loading indicator while the AI cover letter is generating (Minor/UX)

**Journey:** Application Editor → Cover Letter → "Generate with AI."
**Repro:** Open the cover letter editor for a job, click the sparkle "Generate cover letter with AI" button.
**Actual:** The request (`POST /cover-letters/create/text`) took about 13 seconds end-to-end in this test. During that entire time the sparkle icon and the rest of the UI show no change at all — no spinner, no disabled state, no "Generating…" text.
**Why a user cares:** A user has no feedback that their click registered, and combined with finding #1 (where clicks silently doing nothing is already a pattern in this app), a plausible reaction is to click the button again, potentially firing a duplicate generation request.
**Note:** once it completed, generation worked well — a full, sensibly-written cover letter was produced and correctly auto-uploaded ("Saved to server").

### 6. "Job not found" server error when checking CV status for a job that hasn't been swiped yet (Medium confidence)

**Repro (best reconstruction):** Open the Application Editor / CV row for a job card directly from the deck, without first liking or disliking that card (so it was never sent to `POST /jobs/create` and doesn't exist in the `jobs` collection yet). CV upload and download for that job worked fine in this session (`POST /cv/upload` → 201, `GET /cv/<key>` → 200), but the backend log later showed:
```
Error checking CV status Error: Job not found
    at file:///Users/ole/VS Code Workspace/jobMatchServer/src/database/database.ts:27:33
```
for that same job's `duplicateKey` (`linkedin:4460974252`, the Delivery Hero listing), a few minutes after the CV actions.
**Why a user cares:** the CV/cover-letter storage is documented as scoped purely by `duplicateKey` (independent of the `jobs` collection), so a status check throwing "Job not found" for a job that was never explicitly created suggests a code path that assumes the job row always exists. Worth a look even though the exact UI trigger isn't fully pinned down — I did not manage to reproduce it a second time in the remaining review time.

### 7. Minor copy bug: singular "keyword" at count 1 (Polish)

**Repro:** Search page, add one keyword.
**Actual:** Footer reads "1/5 keyword" instead of "1/5 keywords" (or a properly pluralized string).
